1. Overview

A single-page web app for planning third-party risk assessments. It has four modules for everyone (Executive Summary, Analytics, Program View, Roster) and one Manager-only module (User Management).

  • Stack: Google Apps Script backend (.gs) plus an HtmlService frontend (.html), with a Google Sheet as the database.
  • Data flow: browser → google.script.run → top-level .gs functions → Google Sheets. There is no REST API.
  • Identity: resolved only on the server with Session.getActiveUser().getEmail(). The browser never asserts a role.
  • Authorization: every public server function calls authorize_() first, which looks the caller up in the Users tab. User Management is the single source of truth for who gets in and with which role (Manager or Reviewer).
  • Database location: the spreadsheet ID lives in the Script Property SPREADSHEET_ID. It is never hardcoded. The Roster subtitle shows the live value.
  • Server contract: every server function returns {success, data} or {success:false, error}. Public functions that write take a script lock (LockService) for the whole transaction.
  • No external resources: the fonts (Geist) are embedded in Fonts.html as data URIs. There are no CDNs.
  • Scopes: spreadsheets and userinfo.email only. There are no libraries, no Advanced Services and no UrlFetchApp.

3. Before you start: Workspace prerequisites

Corporate Workspace tenants often restrict Apps Script. Confirm these with the Verizon Google Workspace administrators before building anything:

  1. Apps Script is enabled for the deploying account's organizational unit.
  2. Web app deployment with access "Anyone within verizon.com" is permitted.
  3. OAuth scopes: the app requests https://www.googleapis.com/auth/spreadsheets and https://www.googleapis.com/auth/userinfo.email. If API Controls restrict third-party or internal apps, the admins may need to mark the script's OAuth client as trusted. Some tenants also require a standard (non-default) Google Cloud project; if so, attach it under Project Settings → Google Cloud Platform (GCP) Project before the first authorization.
  4. Data classification: confirm that third-party risk data may be stored in a Google Sheet in the deploying account's Drive, and that this sharing model meets the data-handling policy.
  5. Deploying account: decide which account owns the project and the spreadsheet. Prefer a long-lived team or service-style account over an individual's account, so the app is not tied to one person's employment. The owner is the first Manager and always keeps full edit rights to the spreadsheet.
  6. Where the database lives: My Drive or a shared drive both work (since v9). setupDatabase() always creates it in the deploying account's My Drive. To use a shared drive, move it there afterwards. A move keeps the file ID, so SPREADSHEET_ID stays valid; a copy gets a new ID that must be entered in Script Properties. Moving it needs permission to add files to that shared drive, and the tenant's settings must allow the move. Files owned by a personal account usually can't be moved into a Verizon shared drive. See section 8, "Database in a shared drive".

4. Choose the access model

Inside one Workspace domain, Google discloses each visitor's e-mail even when the app runs as its owner. That makes a stricter model possible than the one the sandbox needed.

Model A needs one Script Property: SHARE_DATABASE_WITH_USERS = false (section 7). With it, User Management stops sharing the spreadsheet with each user and revokes any share it made earlier, so the spreadsheet is reachable only through the app. The Users and Config protections are still managed. 6. Production setup, step by step

Sign in to Chrome with the verizon.com deploying account first. Use a separate Chrome profile, so the personal sandbox account can't be picked by mistake.

  1. Create the project. Go to script.google.com → New project and rename it, for example "TPRM Assessment Planner".
  2. Show the manifest. Go to Project Settings → tick "Show 'appsscript.json' manifest file in editor".
  3. Add the files listed in section 5 with exact names: Script files Code, Config, DB, Users, ThirdParties, LinesOfBusiness; HTML files Index, Fonts, Stylesheet, JavaScript, README. Paste each file's content whole and unmodified, replacing the editor's default text. Skip Seed.gs in production.
  4. Set the manifest webapp block for the chosen access model (section 4) and set timeZone. For Model A, also add the Script Property SHARE_DATABASE_WITH_USERS = false now (Project Settings → Script Properties), before running setup.
  5. Save (Ctrl+S). Open each file and check that there are no red error markers.
  6. Create the database. Select setupDatabase in the function list (Config.gs) → Run → approve the authorization prompt. This:
    • creates the spreadsheet "TPRM Assessment Planner — Database" in the owner's My Drive;
    • stores its ID in the Script Property SPREADSHEET_ID;
    • creates the ThirdParties, LinesOfBusiness, Config and Users tabs with their headers;
    • fills Config with the default dropdown values;
    • registers the account that ran it as the first Manager;
    • protects the Users and Config tabs.
    The Execution log only shows "Execution completed". Confirm success with the next step.
  7. Verify. Check that Project Settings → Script Properties shows SPREADSHEET_ID. Open the spreadsheet (Drive → "TPRM Assessment Planner — Database") and check:
    • the four tabs exist;
    • ThirdParties has 20 headers (A–T);
    • Users has exactly one row, the owner, as Manager;
    • Users and Config show a padlock.
  8. Deploy. Go to Deploy → New deployment → type "Web app" and set:
    • Description: "v1";
    • Execute as: per the model;
    • Who has access: Anyone within verizon.com.
    Click Deploy and copy the /exec URL. Store that URL in your team's runbook, not in this file.
  9. Smoke test as the owner. Open the /exec URL and check:
    • all modules render;
    • Roster shows the spreadsheet ID as its subtitle;
    • adding, editing and deleting a test third party updates the ThirdParties tab;
    • dark mode survives a reload.
  10. Add users in User Management with their exact verizon.com e-mail and role. Then have one Reviewer and one more Manager sign in and confirm what each can see and do.

8. The database spreadsheet

Column order in the *_HEADERS arrays (Config.gs) is the source of truth. Don't reorder, insert or rename columns by hand. Other tabs

  • LinesOfBusiness: lob_id, tp_id, line_of_business, service_description, vendor_manager. Rows are removed together with their third party.
  • Users: email, first_name, last_name, role (Manager or Reviewer), added_at. Protected; edit it through User Management only.
  • Config: config_key, config_value, with one row per dropdown option. Protected. The keys are: status, region (NA, LATAM, EMEA, APAC, US), assessment_type, framework, role, supplier_type (Tier 1, TPD, SaaS, Logistics, Tier 2, Review, Tier 1 OR, VIS, TF Project, Frontier) and infosec_version (4.1, 4.2).

Database in a shared drive

  • A move into a shared drive keeps the file ID, so nothing changes in Script Properties. Run initializeSheets() once afterwards.
  • Google reports no owner for shared-drive files. The app then:
    • leaves access that comes from shared drive membership alone, because that belongs to the drive's managers;
    • still adds or revokes the per-file shares it made itself (tracked in APP_SHARED_EDITORS);
    • still manages the Users and Config protections.
  • Shared drive members can edit the spreadsheet directly, including people who aren't in User Management, and Users/Config protections aside. Keep the drive's membership to the people who administer the app, or keep the database in the owner's My Drive with Model A.
  • First-time setup (no Manager yet) is refused in a shared drive, because there is no owner to recognise. Always create the database with setupDatabase() first, then move it.

Changing dropdown options

The app reads options from the Config tab, and the order of the rows is the order shown in the UI. To add an option, add a row (Manager or owner). To retire one, remove it from both the Config tab and DEFAULT_CONFIG in Config.gs: initializeSheets() re-adds any default value that is missing from the sheet. Records that already use a retired value keep it, but they can't be saved until it is changed to a valid option.

Schema changes

  • New column: append the key to the end of TP_HEADERS (or the relevant array), deploy, then run initializeSheets(). It writes the missing headers on the right without moving any data.
  • Renamed column or Config key: add the mapping to HEADER_RENAMES or CONFIG_KEY_RENAMES, then run initializeSheets(). It rewrites the old name in place and keeps the data.
  • initializeSheets() can be run again safely at any time. It never deletes or reorders data, and it stops with a clear error if a header doesn't match.

9. User management and access control

  • Managers can use every module, including User Management, and can hard-delete third parties. Reviewers can use Executive Summary, Analytics, Program View and Roster, and can create and edit records.
  • At least one Manager must always remain; the server refuses to remove or demote the last one.
  • Adding, editing or removing a user (and every initializeSheets() run) runs syncAccess_(), which:
    • with sharing on (Model B, sandbox), shares the spreadsheet with every listed user;
    • always protects the Users and Config tabs so only Managers and the owner can edit them directly;
    • revokes access User Management no longer grants. In My Drive that means every editor or viewer not listed; in a shared drive, only the app's own shares. With sharing off (Model A), every share the app made earlier is revoked. The owner is never touched.
    If part of the sync fails, for example an address that isn't a Google account, the rest still runs and the message lists what couldn't be done.
  • Someone not listed sees "You don't have access yet". If Google withholds a visitor's e-mail, they see an explanation instead. In a Workspace domain this should only happen to accounts outside verizon.com.
  • The Manager/Reviewer toggle in the top bar only previews the Reviewer view. The server always enforces the real role.

10. Shipping code changes

  1. Make and test the change in the sandbox first.
  2. In production, paste the changed files whole into the editor and save. The live app keeps running the previous version until you deploy.
  3. If the change touches columns or Config keys, run initializeSheets() before deploying (section 8).
  4. Go to Deploy → Manage deployments → select the active deployment → Edit (pencil) → Version: New version. Add a description, check that "Execute as" and "Who has access" are unchanged, and click Deploy. The /exec URL stays the same.
  5. To roll back, Edit the deployment and pick an earlier version. For a staging check before deploying, Deploy → Test deployments gives a /dev URL that always runs the latest saved code (owner and editors only).

11. Moving data from the sandbox (optional)

Production normally starts empty. If sandbox records must move over:

  1. Set up production completely (section 6) so that its headers exist.
  2. In the sandbox spreadsheet, copy the data rows (not the header row) of ThirdParties and LinesOfBusiness.
  3. In production, paste with Paste special → Values only, starting at row 2, columns A–T and A–E. Keep the tp_id and lob_id values as they are, so LinesOfBusiness rows still point to their third party.
  4. Do not copy Users or Config. Add the production users through User Management.
  5. Reload the app and spot-check a few records in the Roster and the record panel.
The sandbox's demo vendors (TP-0001 to TP-0031) are fictional. Leave them behind.

12. Operations and troubleshooting

SymptomLikely cause and fix
"You don't have access yet"The account isn't listed in User Management, or it is signed in with a different Google account. Under Model B, the user may not have edit access to the spreadsheet yet. Re-save the user to re-run the sync. Check that SHARE_DATABASE_WITH_USERS isn't false under Model B.
"The user list was saved, but database sharing could not be fully updated: …"The listed items failed and everything else was applied. Typical causes: an address that isn't a Google account, a shared drive that blocks sharing with non-members, or a tenant sharing policy. Fix the cause and re-save the user, or run initializeSheets().
"Google did not share your account email…"The visitor is signed in with an account outside verizon.com, or the browser has several accounts and a non-Workspace one is active.
"Sorry, unable to open the file at this time"Google blocked the visit before the app loaded. Check the deployment's "Who has access" and that the visitor uses a verizon.com account.
"SPREADSHEET_ID is not set…"The Script Property is missing. Restore it to the existing database's ID. Don't run setupDatabase(), which would create a new, empty database.
"Sheet … has an unexpected header…"Someone edited a header row by hand. Restore the header named in the message, then run initializeSheets().
"The system is busy"Another save held the script lock for over 30 seconds. Retry.
A save is rejected with "Invalid …"The value isn't in the Config tab, for example a retired dropdown option. Pick a valid option, or add it back to Config.

Server errors are logged to Cloud Logging (exceptionLogging: STACKDRIVER) and appear under the project's Executions page.

13. Security notes and known limitations

  • include() is allow-listed (since v9) to Fonts, Stylesheet and JavaScript, which the browser receives anyway. Any other name, including README and Index, is refused. If you add a page part that Index includes, add its name to INCLUDABLE_FILES_ in Code.gs.
  • Model B only: every listed user is an editor of the spreadsheet, so they can edit the ThirdParties and LinesOfBusiness tabs directly, outside the app's validation and role rules. Model A with SHARE_DATABASE_WITH_USERS = false closes this.
  • Shared drive: drive members have direct edit access that the app doesn't manage (section 8).
  • Demoting yourself: a Manager who demotes themselves stays on the Users and Config protection list until another user change runs the sync. Google doesn't let an account remove itself from a protection in the same action.
  • Owner: the spreadsheet owner can always edit everything. Plan an ownership hand-over if that person changes role.
  • Seed.gs loads demo data into an empty roster when a Manager runs it. Keep it out of production.
  • Browser storage: only the dark-mode preference is kept in the browser (localStorage). No business data is cached there.
